# Performance (Phase 6b)

How fast Evenly feels, how it's measured, what slows it down, and what was done about it. Plan and targets: `docs/rebuild-plan.md` § 6b.

## How to measure

- **In-app marks** (`src/lib/perf.ts`): `js-ready`, `firebase-ready`, `auth-ready`, `snapshot:<trips|trip|expenses>:<cache|server>` (with the document count), `painted:<welcome|home|trip|form>` (first frame showing the screen's data), `save:tap`, `save:confirmed`. Cheap; read only by the tools below.
- **Web harness** `node scripts/perf.mjs [--size typical|big|stress] [--network slow|good] [--runs 5] [--no-build] [--label x]`: production build against the emulators (`npm run emulators` first), Pixel 7 viewport, CPU 4× slower; "slow" = 150 ms latency, 1.6/0.75 Mbps (Lighthouse mobile), "good" = 40 ms, 9/3 Mbps. Sizes: main trip with 6 people·40 expenses / 8·150 / 20·1000, plus two small trips. Medians; JSON in `perf-results/` (gitignored). It refuses to run on a slow emulator (see the gotcha below).
- **Android runner** `node scripts/perf-android.mjs [--runs 5]`: the debug APK (`npm run android:dev`) on a device or AVD; clears the debug app's data, seeds a "big" user, then per run: force-stop → `am start -W` → marks over the WebView's DevTools → open trip → Add expense → Save.
- **`?perf` panel** (`src/app/PerfPanel.tsx`): open the site once with `?perf` (`?perf=off` to stop) and every launch shows the marks on screen: real numbers from a real phone (iPhone included) against the real project.
- **Gotcha**: a Firestore emulator that has run for hours (many e2e/perf sessions) can slow to ~2 s per write (a fresh one: ~20 ms). That, not the app, made trip creation look like 2 s and was behind the slow first write in the PDF e2e tests. Restart it before measuring.

## Typical trips (2026-10-28, user's focus: small trips, launch, loading, adding an expense)

Web, typical trip (6 people, 40 expenses), slow network, CPU 4×, median of 3, ms: returning launch → trips 735 (Auth's server check of the saved login takes ~300 of it, see below); first visit to a trip 678 (expenses from the server); trip seen before 141; Add expense → form 28; Save → listed 85; name entered → Home 1190; first open → name 2259 (downloading 317 kB).

- **F9 done**: Home holds its top 3 trips' listeners (`holdTrip`), so opening one finds the data ready: first visit on a device 692 → 133. Trips the server doesn't have yet (just created here) aren't held: the server would refuse the listen and the trip would look lost.
- **Web launch waits on Auth**: on start the Auth JS SDK always re-checks the stored user with the server (`accounts:lookup`, plus a token refresh when the saved token is over an hour old) before the first auth state, and Firestore waits for that user even to read its offline cache. The native SDKs don't (Android: auth-ready ~130 ms on the S25). **F10 done** (user OK, APP-10, ADR 0007): on the web, Home shows a copy of the last visit's list while Auth checks: returning launch → trips 735 → 384. Tapping a trip in the first ~0.4 s still waits for Auth (harness, which taps at once: trip 133 → ~440), so launch → trip open is about the same in total (~0.85 s); the list just shows sooner.

## Firebase research (2026-10-28)

What the docs and reports say, and what it means for Evenly.

| Topic                                  | What we learned                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | For Evenly                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Auth start-up check**                | On every start, Firebase Auth (web) re-validates the stored user with the server (`accounts:lookup`) before the first auth state; others measured 400–500 ms ([zenn.dev notes](https://zenn.dev/mythosil/scraps/303c29af747a13), [firebase-js-sdk#8478](https://github.com/firebase/firebase-js-sdk/issues/8478), [#6175](https://github.com/firebase/firebase-js-sdk/issues/6175)). There's no setting to skip it, and Firestore waits for Auth's user before answering even from its cache. Offline, the check fails fast and the stored user is used.                                                                                                                                                                         | Can't be removed without a manual cache of the session (against our live-data rule). F2 already removed the popup library that came before it. Accept.                                                                                                                                                                                      |
| **Writes: don't await**                | `setDoc`/`updateDoc` promises resolve only when the server acknowledges; the local cache and listeners update immediately (latency compensation). Recommended: don't await, `.catch` real failures ([setDoc](https://doc.deno.land/https://esm.sh/@firebase/firestore@4.16.0/dist/index.d.ts/~/setDoc), [updateDoc](https://doc.deno.land/https://esm.sh/@firebase/firestore@4.16.0/dist/index.d.ts/~/updateDoc), [offline persistence guide](https://oneuptime.com/blog/post/2026-02-17-how-to-enable-offline-persistence-in-firestore-for-web-applications/markdown)). A `getDoc` from the server right after a pending `setDoc` waits for it ([report](https://www.technetexperts.com/firestore-getdoc-hangs-after-setdoc/)). | Done for expenses (F1). The same applies to every other write (create trip, guests, rename, leave, invite): they could all return at once. Our only one-off read (`myTripsForWrite`) reads Home's query, not a just-written document.                                                                                                       |
| **Offline writes**                     | Writes made offline are queued in the local cache and sent when back online, across restarts (persistent cache).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | APP-6 disables writes offline today. With F1 they'd just work (queued). A product decision for later: allow adding expenses offline.                                                                                                                                                                                                        |
| **Read costs**                         | With offline persistence, a listener that reconnects within 30 minutes is billed only for changed documents; after 30+ minutes offline it's billed as a new query. Deleted documents leaving a result aren't billed ([Firestore pricing](https://cloud.google.com/firestore/pricing)). A full reload re-listens ([forum](https://forums.expo.io/t/firestore-extra-reads-on-reload-and-hard-refresh/45139)).                                                                                                                                                                                                                                                                                                                      | Each app launch after 30+ minutes re-reads Home's trips and each opened trip's expenses: ~50–150 reads per trip opened. Spark's 50k reads/day leaves a lot of room at our size. Prefetching (F6) would add reads; only worth it for the most recent trip.                                                                                   |
| **Bundle size**                        | Firestore Lite is 70–84% smaller but has no `onSnapshot`/persistence ([Firestore Lite](https://firebase.google.com/docs/firestore/solutions/firestore-lite), [blog](https://firebase.blog/posts/2023/03/trim-javascript-bundles-firestore-lite)); splitting out realtime code doesn't shrink the full SDK ([cur.at](https://cur.at/qvLf5z9?m=web)).                                                                                                                                                                                                                                                                                                                                                                              | Not usable: everything on screen is live. The full SDK (~150 kB gz) stays; F3 makes it download in parallel; the service worker serves it on later launches.                                                                                                                                                                                |
| **Multi-tab cache**                    | `persistentMultipleTabManager` (what the plugin uses with `synchronizeTabs: true`) coordinates queries and writes across tabs; the single-tab manager does no cross-tab sync ([single-tab](https://firebase.google.com/docs/reference/js/firestore.persistentsingletabmanagersettings), [multi-tab](https://firebase.google.cn/docs/reference/js/firestore_.persistentmultipletabmanager?hl=en)). No published start-up comparison.                                                                                                                                                                                                                                                                                              | Worth a quick experiment (one setting); single-tab means a second tab of the site would run without the offline cache.                                                                                                                                                                                                                      |
| **Transport**                          | Long-polling auto-detection is on by default since 9.22; forcing long-polling costs performance; turning detection off is a diagnostic step ([FirestoreSettings](https://firebase.google.com/docs/reference/js/firestore.firestoresettings)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Keep the defaults.                                                                                                                                                                                                                                                                                                                          |
| **Native plugin vs JS SDK on Android** | The Capawesome plugins run the native Android SDKs and pass results over the Capacitor bridge ([plugin](https://capawesome.io/plugins/firebase/cloud-firestore)); no published performance comparison with the JS SDK in the WebView. The JS SDK works in Capacitor with `initializeAuth` + IndexedDB persistence ([Ionic forum](https://forum.ionicframework.com/t/firebase-auth-in-sdk-9-does-not-work-on-ios-sim-or-devices/215362), [custom Auth dependencies](https://firebase.google.com/docs/auth/web/custom-dependencies)).                                                                                                                                                                                              | Our Android numbers (Home → trip ~600 ms vs ~290 ms on the throttled web) hint the native path + bridge costs more. **But** switching Android to the JS SDK changes where the anonymous identity is stored: every Android user would get a new identity and need a relink (no backend to transfer it). Measure first (below), decide later. |
| **Emulator slowdown**                  | The emulator uses simple locking and can lag under concurrent writes to one document (locks up to 30 s); its data can be cleared with a REST call without a restart ([Firestore emulator](https://docs.cloud.google.com/firestore/docs/emulator)). Nothing documents a gradual slowdown.                                                                                                                                                                                                                                                                                                                                                                                                                                         | Ours slows to 0.4–2 s per write after a few e2e/perf sessions. Try clearing its data (instead of restarting) when it's slow; if that fixes it, the harness can do it automatically.                                                                                                                                                         |

### Proposed next steps from the research

1. **R1** Return at once from every write, like F1 (create trip, add/rename/remove guest, rename trip, leave, invite code), each with a notice if the server refuses. Behavior change: specs + your OK.
2. **R2** Experiment: single-tab Firestore cache on the web; keep it only if launch gets measurably faster.
3. **R3** Experiment: the same build in Chrome on the Android emulator (JS SDK) vs the APK (native plugins), same device, same data; if the JS SDK is clearly faster, propose a plan for moving Android to it, including relinking existing Android users.
4. **R4** Emulator: clear its data when it's slow; automate in the harness if it works.
5. Later product question: allow adding expenses offline (APP-6), now that writes are queued anyway.

### Results of R1–R4 (2026-10-28)

- **R1 done** (APP-9): renaming a trip, adding/removing a member, leaving, deleting and the name's copies in trips take effect at once. Creating a trip keeps waiting: a trip opened before the server has it shows "Trip not found" (rules deny reading a document the server doesn't have yet). Joining and invite codes wait too.
- **R2 done**: single-tab Firestore cache on the web. Big trip, slow network: returning launch 805 → 716 ms, trip seen before 308 → 247 ms. A second tab falls back to a memory cache (Firestore does this itself on `failed-precondition`).
- **R4 done**: clearing the emulator's data brings writes back to ~30 ms; `scripts/perf.mjs` does it (and re-seeds the demo trip) when writes are slow.
- **R3 measured**, same AVD, same data (big trip), same build, emulators on the LAN:

| Step                                     | APK (native plugins) | Chrome on the same device (JS SDK) |
| ---------------------------------------- | -------------------: | ---------------------------------: |
| Signed in → trips from the offline cache |                  420 |                                120 |
| Home → trip with expenses (seen before)  |                  773 |                                269 |
| Save → back on the trip                  |                  168 |                                142 |
| Add expense → form                       |                   36 |                                 29 |

Turning off the debug build's bridge logging (`loggingBehavior: "none"`) changed nothing (758 ms to open the trip). The native Firestore path plus the bridge is ~3× slower at reading data than the JS SDK in the same WebView. (Start-up isn't compared: the Chrome run reloads a tab in a warm browser; the APK cold start includes Android and WebView start-up, ~1.7 s on the AVD.)

**Proposal R5**: run the Firebase JS SDK on Android too (drop the Capacitor Firebase plugins): one code path on every platform, faster data on Android, a smaller APK. Cost: the anonymous identity lives in the native SDK and can't be handed to the JS SDK without a backend, so every Android user gets a new identity once and needs a relink (`scripts/relink.ts`, as done before). Needs an ADR and the user's OK. **Decision (2026-10-28): not now**; revisit after the real-phone measurements (rebuild-plan 6b step 6).

Both as APKs on the same AVD (`node scripts/android.mjs dev --js-sdk` vs `npm run android:dev`), big trip: cold start → trips (page clock) 1213 → 1007 ms, Home → trip 760 → 431 ms, Save 162 → 187 ms (noise). The JS-SDK build reaches the emulators over plain HTTP from the app's https://localhost page, so that build alone allows mixed content (`capacitor.config.ts`); against the real project everything is HTTPS.

**Real phone (2026-10-28)**: Galaxy S25 (SM-S931B, Android 17), debug APKs over Wi-Fi against this PC's emulators, big trip, median of 5, ms:

| Step                                      | Native plugins | JS SDK |
| ----------------------------------------- | -------------: | -----: |
| Android launch (`am start` TotalTime)     |            310 |    291 |
| Cold start → trips on screen (page clock) |            224 |    224 |
| Home → trip with expenses                 |            151 |     95 |
| Add expense → form ready                  |              9 |      9 |
| Save → back on the trip                   |             37 |     35 |

Every journey is well inside its target on both. The JS SDK only wins on opening a trip (~55 ms), not worth giving every Android user a new identity. **R5: no** (keep the native plugins); the `--js-sdk` build stays for a re-check on a slower phone. The S25 is high-end: a mid phone is ~3–4× slower on scripting, which the lab harness's 4× CPU throttle already covers.
