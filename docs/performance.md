# Performance (Phase 6b)

How fast Evenly feels, how it's measured, what slows it down, and what was done about it. Plan and targets: `docs/rebuild-plan.md` § 6b.

## How to measure

- **In-app marks** (`src/lib/perf.ts`): `js-ready`, `firebase-ready`, `auth-ready`, `snapshot:<trips|trip|expenses>:<cache|server>` (with the document count), `painted:<welcome|home|trip|form>` (first frame showing the screen's data), `save:tap`, `save:confirmed`. Cheap; read only by the tools below.
- **Web harness** `node scripts/perf.mjs [--size typical|big|stress] [--network slow|good] [--runs 5] [--no-build] [--label x]`: production build against the emulators (`npm run emulators` first), Pixel 7 viewport, CPU 4× slower; "slow" = 150 ms latency, 1.6/0.75 Mbps (Lighthouse mobile), "good" = 40 ms, 9/3 Mbps. Sizes: main trip with 6 people·40 expenses / 8·150 / 20·1000, plus two small trips. Medians; JSON in `perf-results/` (gitignored). It refuses to run on a slow emulator (see the gotcha below).
- **Android runner** `node scripts/perf-android.mjs [--runs 5]`: the debug APK (`npm run android:dev`) on a device or AVD; clears the debug app's data, seeds a "big" user, then per run: force-stop → `am start -W` → marks over the WebView's DevTools → open trip → Add expense → Save.
- **`?perf` panel** (`src/app/PerfPanel.tsx`): open the site once with `?perf` (`?perf=off` to stop) and every launch shows the marks on screen: real numbers from a real phone (iPhone included) against the real project.
- **Gotcha**: a Firestore emulator that has run for hours (many e2e/perf sessions) can slow to ~2 s per write (a fresh one: ~20 ms). That, not the app, made trip creation look like 2 s and was behind the slow first write in the PDF e2e tests. Restart it before measuring.
